用户最初提供的《TradeFlow Lite 产品需求与架构文档 v0.1》只用于帮助理解项目背景，不是需求依据、设计依据或后续权威文档。本文只记录后续对话中已经明确讨论的内容。每讨论清楚一项，就直接更新本文，并区分：

## 二、产品定义

### 2.1 产品名称

TradeFlow Lite

### 2.2 产品定位

TradeFlow Lite 是 TradeFlow 旗下免费、开源、轻量级的专业行情图表工具。

它面向普通交易用户，不要求用户理解 GitHub、编程、部署或开发环境。普通用户下载安装后应当可以直接看盘。

### 2.3 Lite 与 TradeFlow Pro 的关系

Lite 不是免费的 TradeFlow Pro，也不是明显残缺的广告壳。

Lite 的主体能力来自 TradeFlow 已经具备并验证过的能力子集。除本文明确列出的开放数据接入、开放 AI 接入和动态指标生态外，原则上不优先开发 TradeFlow 主项目中不存在的大型产品能力。

Lite 应当可以独立完成基础看盘。具体包含哪些 TradeFlow 能力、哪些能力只保留在 Pro，后续逐项讨论，不从最初文档自动继承。

## 四、产品形态

### 4.1 macOS 客户端

- 正式产品；
- 官网下载 DMG；
- 内置 Rust TDX 行情客户端；
- 用户不安装 Python、Rust 或 Node；
- 系统差异只放在 macOS 薄适配层。

### 4.2 Windows 客户端

- 正式产品；
- 官网下载安装包；
- 与 macOS 共用前端、业务规则和主程序；
- 系统差异只放在 Windows 薄适配层。

### 4.3 Web Demo

- 使用与桌面端相同或高度一致的前端界面；
- 使用固定、模拟或明确标注的演示数据；
- 不承诺正式实时行情；
- 不在浏览器中直连行情主站；
- 主要用于产品展示、内容传播和引导下载桌面端。

Web Demo 不得让用户误以为演示数据是正式实时行情。

### 4.4 官网：普通用户主渠道

官网面向不懂编程的普通用户，也是 Lite 的主要目标人群和主要发布渠道。

官网应当提供：

- 简单易懂的产品介绍和能力说明；
- macOS、Windows 安装包下载；
- 面向普通用户的安装、使用和常见问题说明；
- 清楚展示当前版本、系统要求和更新内容；
- Web Demo 入口，用于在下载前了解产品；
- 必要的开源说明和 GitHub 入口，但不要求普通用户阅读源码仓库才能完成安装或使用。

官网用户路径应尽量保持为：

```text
了解产品 → 体验 Demo（可选）→ 下载对应安装包 → 安装后直接使用
```

普通用户不需要安装 Python、Rust、Node，不需要克隆仓库，也不需要自行构建。

### 4.5 GitHub：开发者与社区生态渠道

GitHub 用于：

- 公开客户端源码；
- 提供可复现的构建说明、开发文档和更新记录；
- 允许开发者 Fork 后自行开发和维护自己的版本；
- 接受 Issue 和 PR；
- 接受社区贡献的技术指标实现；
- 提供数据适配器模板；
- 未来提供社区适配器和社区扩展。

GitHub 面向数量较少但长期重要的开发者用户。它不是普通用户的主要使用入口，也不应成为安装 Lite 的必经步骤；但未来技术指标、数据适配器和其他可开源扩展的社区贡献，主要依靠这条渠道积累。

社区提交进入官方主干前仍需经过代码审查、许可检查和实际验证。允许 Fork 和自行开发，不代表所有 PR 都会自动合并，也不代表社区版本由 TradeFlow 官方负责支持。

### 4.6 两条发布线的关系

```text
同一份已验证的 Lite 源码与版本
              │
       ┌──────┴──────┐
       ▼             ▼
官网主发布线       GitHub 开源线
普通用户           开发者与贡献者
安装包 + 简明说明   源码 + 构建文档 + Issue/PR
       │             │
       ▼             ▼
直接安装使用       Fork、二次开发、贡献指标和适配器
```

两条线对应同一个 Lite 产品，不维护互相分叉的“官网版”和“GitHub 版”。正式版本应能追溯到对应源码版本；具体是否同时在 GitHub Releases 提供安装包，后续在发布方案中确定。

### 4.7 本地优先与版本更新

“完全开源、透明”和“主要能力在用户本地运行”，不等于客户端永远不能联网。行情请求、用户自选、设置、指标计算和 AI 配置等产品数据可以留在本地；但普通用户要自动知道有新版本，客户端必须访问一个公开的更新来源。

建议采用静态更新清单，不建设账号或业务更新服务：

```text
Lite 启动或用户点击“检查更新”
              ↓
读取公开的 latest.json
              ↓
本地比较当前版本和最新版本
              ↓
发现新版后展示版本号、更新说明和下载按钮
              ↓
下载签名更新包并在本地验签后安装
```

这条连接只承担软件发布，不承载行情、用户数据、账号、遥测或远程控制。更新检查失败时，Lite 仍可继续使用现有版本，不得因为更新服务不可用而阻断看盘。

可选托管方案：

1. **官网静态存储/CDN为主，GitHub Releases 镜像或备用**：更适合主要普通用户，官网下载安装与应用内更新保持一致，也更容易保证访问稳定；
2. **只使用 GitHub Releases**：不连接 TradeFlow 自有服务，维护量最低，但普通用户所在网络访问 GitHub 不稳定时，可能无法及时收到更新。

当前建议采用第一种。这里需要的只是可公开缓存的版本 JSON、安装包和签名文件，不需要长期运行动态后端。客户端应公开更新地址和检查逻辑，不使用设备 ID，不要求登录，不上传自选、行情或使用行为。服务器或 CDN 仍会像普通 HTTPS 下载一样看到请求 IP；隐私说明中应如实披露这一点。

更新包必须签名，客户端内置公钥验证，发布私钥不能进入开源仓库。公开源码不等于公开签名私钥；私钥一旦公开，任何人都能伪造“官方更新”。

自动检查是否默认开启、检查频率、是否自动下载，以及 GitHub 是否作为正式备用地址，后续在发布方案中确认。即使自动检查开启，也应由用户确认安装，不做无提示的强制升级。

## 五、总体架构

### 5.1 架构目标

1. 尽量复用 TradeFlow 已验证能力，缩短首版开发周期；
2. Mac、Windows 共用同一主干，避免形成两个产品；
3. Lite 保持独立、开源、可构建，不依赖 TradeFlow 私有仓库才能运行；
4. 主程序保持小而稳定；
5. 后续数据适配、AI 适配和动态指标生态不要求重写图表、自选和基础指标；
6. 不因“开源扩展”而允许任意代码直接获得系统和密钥权限。
7. 官网安装包与 GitHub 源码来自同一版本主干，不形成两套产品实现。
8. 更新服务与产品运行解耦：无法检查更新时不影响本地看盘，更新检查不成为遥测或账号入口。

### 5.2 总体分层

```text
┌────────────────────────────────────────────────────┐
│                 Shared Frontend                    │
│ 图表 / 搜索 / 自选 / 内置指标 / 设置 / AI 对话（以后）│
└──────────────────────┬─────────────────────────────┘
                       │ 统一应用接口
┌──────────────────────▼─────────────────────────────┐
│               Shared Desktop Core                 │
│ Tauri / Rust 主干、统一合同、任务调度、本地存储      │
└───────────────┬───────────────────────┬────────────┘
                │                       │
┌───────────────▼─────────────┐  ┌──────▼──────────────┐
│      Data Provider 层       │  │ AI Provider + Tools │
│ Rust TDX / 用户适配器（以后） │  │ 用户自带AI API（以后）│
└───────────────┬─────────────┘  └─────────────────────┘
                │
┌───────────────▼─────────────┐
│        Rust TDX Client      │
│ 协议、主站、原始行情与除权数据 │
└─────────────────────────────┘

平台薄适配层：
macOS：路径、窗口、菜单、签名、公证、DMG
Windows：路径、窗口、菜单、WebView2、签名、安装包
```

### 5.3 共享主干原则

Mac 和 Windows 必须共享：

- 同一套前端；
- 同一套数据合同；
- 同一套周期、时间和行情规则；
- 同一套指标计算；
- 同一套自选和设置模型；
- 同一套 Rust 行情请求与恢复行为；
- 同一套错误语义和诊断信息。

薄适配层只处理无法跨平台统一的系统能力，不得复制业务逻辑。

### 5.4 当前实现边界

Lite 当前直接使用独立 Rust TDX 协议客户端，不包含行情 sidecar 或第三方 TDX 客户端运行依赖。前端只接收稳定的 Lite 数据合同，不接触协议报文。

Lite 继续复用主项目已验证的产品行为、周期、时间、前复权、结果校验、自选持久化和跨平台经验，但不复制主项目私有业务、账户、Pine、服务器、期货、扩展指数、部署配置、密钥或无法确认开源许可的第三方资产。

协议、主站、图表和第三方素材分别接受真实数据测试与许可审计；复用行为不等于复制实现。

## 六、桌面端数据链路

### 6.1 默认路径

```text
用户操作
  ↓
前端请求统一行情接口
  ↓
Rust 主干负责调度、取消、校验、聚合、前复权和本地状态
  ↓
Rust TDX Client 请求主站，返回原始行情与除权事件
  ↓
返回统一 Symbol / Bar / Quote 数据
  ↓
Lightweight Charts 渲染
```

Rust 负责协议、主站、行情处理和统一合同。前端不得直接依赖协议返回格式，图表只接收 Lite 的统一数据模型。

### 6.2 高可用目标

Lite 不复制 TradeFlow Web 的整套服务器级基础设施，但桌面端需要保留用户可感知的高可用能力：

- 多主站探测和自动切换；
- 不同能力分别记录主站健康状态；
- 超时、冷却和有边界的重试；
- 单次历史请求不拼接不同主站的分页结果；
- 快速切股、切周期时可以取消过时任务；
- 长连接异常后丢弃并自动换站恢复；
- 暂时断线时保留最后一份已验证图表，不清空为假数据；
- 恢复后校验时间顺序和 OHLC，再更新图表；
- 用户可看到简明连接状态，并可导出诊断信息。

具体并发、超时和缓存参数不能凭空设定，后续从主项目现状和真实运行测量中确定。

### 6.3 Lite 主站池边界

Lite 当前内置 19 台经过 Rust 客户端逐台验证的公共标准行情主站，覆盖陕西、浙江、上海、北京、武汉、深圳和广州，并分散在传统运营商及双线 CDN 网络。已确认慢、不稳定或返回数据不一致的地址不进入默认池。

启动时使用独立短连接并发测速，按可用性和延迟排序；业务请求复用一条加锁长连接。切股票、切周期、深历史和报价轮询默认保持同一主站。连接或整次请求失败后丢弃连接并完整换站，禁止把不同主站的部分历史拼成一个结果。

标准行情池与以后可能增加的扩展行情池必须隔离。主站可用性会随外部服务变化，因此每次发布前均需重新执行逐台协议能力验证。

### 6.4 ETF 与指数覆盖核对

Lite 内置市场目录包含 5,570 只股票、1,659 只 ETF 和 556 只沪深北标准指数。目录经过代码、交易所、品种类型、重复项和代表品种合同验证。

19 台默认主站已逐台通过股票日线、1 分钟线、指数日线、行情快照和除权资料请求；真实行情矩阵覆盖沪深北股票、ETF、指数、全部支持周期、两种复权及深历史。主站可用性会随外部服务变化，因此这些结论必须在发布前重新验证。

Lite v0.1 不包含扩展行情、期货或板块指数。静态市场目录随 Lite 版本更新，运行时不从主站下载证券列表。

## 七、统一数据模型

统一数据模型的目的是让图表和业务功能不关心数据来自内置 Rust 客户端、国外数据商还是用户自己的服务。

### 7.1 初步对象

- `Symbol`：统一品种身份、显示名称、交易所、市场、品种类型；
- `SymbolInfo`：价格精度、交易时区、交易时段、支持周期；
- `Bar`：时间、开、高、低、收、成交量及可选成交额；
- `Quote`：最新价、昨收、涨跌、买卖盘等可用字段；
- `ProviderCapabilities`：数据源实际支持的市场、周期、历史和实时能力；
- `ProviderStatus`：连接、限流、认证失败、暂时不可用等状态。

### 7.2 必须统一的语义

- 品种唯一身份；
- 时间戳单位；
- 时区；
- K 线采用开始时间还是结束时间；
- 周期命名；
- 数据排序和去重；
- 交易时段和休市空档；
- 复权状态；
- 无成交、缺失和真正错误的区别；
- 实时更新是覆盖当前 K 线还是增加新 K 线。

这些语义在开始图表和数据接口编码前需要冻结第一版合同。

### 7.3 v0.1 已冻结的数据合同

- 品种范围：内置目录中的 A 股股票、ETF 和沪深北标准指数；期货、扩展指数和板块指数不进入 v0.1；
- 周期：`1`、`5`、`15`、`30`、`60`、`1D`、`1W`、`1M`；
- K 线时间：沿用 TradeFlow 的 K 线结束时间语义和中国市场时区/交易时段规则；
- 排序：传给图表前严格按时间升序、唯一；
- 价格模式：默认 `unadjusted`（不复权），并支持 `qfq`（前复权）；
- 周、月：沿用已验证的“拉取受支持的低周期，再统一聚合”路径，不把图表库或主站的偶然返回当作产品合同；
- 主站切换：一次历史请求必须由同一主站完整完成，失败后整请求切站重试，不拼接多个主站的部分结果；
- 图表渲染前必须校验时间、OHLC、去重和请求身份，过期的切股/切周期结果不得覆盖当前图表。

具体交易日历、停牌、无成交和实时最后一根 K 线更新规则，使用真实主站数据固化为测试。

### 7.4 Rust TDX 当前基线

当前协议层位于 `src-tauri/src/tdx/`，实现连接、两段握手、帧校验、zlib 解压、股票和 ETF K 线、指数 K 线、批量行情快照及除权资料。业务层位于 `src-tauri/src/market_data/`，负责主站测速、长连接复用、整请求切站、分页、数据校验、指数修复、前复权及周月聚合。

行情运行不需要 Python runtime。源码仓库提交 Rust、TypeScript、测试和开发期生成脚本；正式安装包与源码使用同一行情实现。首次公开发布前仍需完成根许可证和全部第三方依赖、UI 素材及绘图扩展的许可审计。

## 八、标准数据源适配能力

### 8.0 当前基础

Rust 行情入口已经增加统一路由层。前端继续使用同一个历史行情合同；路由层根据“市场 + 品种类型”选择适配器，A 股股票、ETF 和指数进入 TDX，数字货币现货和 U 本位永续合约进入 Binance。未接通或请求失败的数据源必须明确返回错误，不得误落到 TDX，也不得跨数据源拼接一次请求。

商品代码搜索弹窗是统一品种入口，目录层级与数据源路由相互独立。例如可以呈现“数字货币 → 现货 → BTC/USDT”，也可以继续增加三级目录；只有叶子品种携带稳定的市场、代码和品种类型，选中后再由 Rust 路由决定实际数据源。目录名称或层级变化不应改变图表请求合同。

Binance 公共行情客户端位于独立 Rust crate `src-tauri/crates/binance-market-data/`，不依赖 Lite、Tauri 或 TDX；Lite 只在 `src-tauri/src/market_providers/binance.rs` 保留薄转换层。Cargo feature `provider-binance` 控制是否编译该模块，关闭后 A 股核心仍可独立构建和测试。当前接入范围为无需 API Key 的 Binance Spot 和 U 本位永续合约公共品种目录、历史 K 线、24 小时行情，以及 `aggTrade + kline + depth20` WebSocket 实时流，不包含账户、下单或用户订单。

实时链路采用“一次只激活当前品种与周期”的订阅合同。切品种、切周期或刷新页面都会生成更大的订阅编号，Rust 端拒绝迟到的旧请求，前端同时核对订阅编号、品种和周期；旧连接消息不得进入新图表。每次连接先用官方 Kline 建立当前 bar 和最后成交 ID 基线，再由连续的 `aggTrade` 即时更新高、低、收；成交量只采信官方 Kline 校准值，避免聚合成交与 Kline 重复计数。重复或过旧事件会被忽略，跨越一个固定周期的首笔成交可直接建立临时 bar，其余不确定状态等待下一条 Kline 整体校准。WebSocket 断开后按上限 15 秒的退避重新连接，连接恢复前保留最后有效数据并使用 REST 低频校准兜底。实时 K 线继续使用统一的结束时间、OHLC 和成交量验证，图表用 `series.update()` 替换当前 bar 或追加新 bar，不重写更早历史；高频事件优先在浏览器下一帧合并绘制，并有 50ms 绘制截止保证前台帧回调异常时不会长时间积压。同一长连接还提供最近聚合成交和 20 档部分深度，前端限频绘制盘口与成交列表。

### 8.1 产品目标

Lite 默认使用自有 Rust TDX 客户端，同时开放标准化的数据源适配协议。

TradeFlow 官方不可能预先适配全世界的数据提供商。用户可以把自己购买的数据商 API 文档交给 AI，由 AI 按 Lite 标准生成可导入的数据适配器；用户导入后只填写自己的 API Key，无需修改 Lite 主程序或手工编程。

### 8.2 用户流程

```text
用户购买数据源
  ↓
把数据商 API 文档交给 AI
  ↓
AI 按 Lite 模板生成 .tfprovider 适配器
  ↓
用户在 Lite 中导入
  ↓
Lite 校验适配器
  ↓
用户单独填写 API Key
  ↓
测试连接并显示支持能力
```

### 8.3 第一层：声明式适配器

为降低开发量和安全风险，优先让 AI 生成声明式配置，而不是任意 Python/JavaScript 程序。

适配器描述：

- 提供商名称和版本；
- 允许访问的 API 域名；
- 认证方式和凭据占位符；
- 品种搜索请求；
- 品种信息请求；
- 历史 K 线请求；
- 实时行情采用 WebSocket 还是轮询；
- 周期、代码和字段映射；
- 时间戳单位和时区；
- 翻页、限流和错误映射；
- 能力声明。

Lite 自己负责真正的联网、密钥注入、数据校验和统一格式输出。

### 8.4 第二层：高级本地桥接

以下数据源可能无法通过声明式配置完成：

- 特殊签名算法；
- OAuth 或交互登录；
- 依赖本地交易客户端；
- 私有 SDK 或二进制协议；
- 特殊 WebSocket 认证。

对于这类数据源，后续允许用户运行一个独立本地桥接服务，再通过 Lite 标准 HTTP/WebSocket 合同连接。高级桥接与 Lite 主程序隔离，不因此把 Lite 变成任意代码执行平台。

### 8.5 适配器验证

启用前至少检查：

- 文件结构和版本是否正确；
- 请求域名是否在声明范围内；
- 适配器内是否错误包含 API Key；
- API 鉴权是否成功；
- 品种身份是否稳定；
- K 线时间是否升序且唯一；
- OHLC 是否满足基本关系；
- 实时数据是否正确覆盖当前 K 线或创建下一根；
- 声明的市场、周期和能力是否实际可用；
- 错误和限流是否能被 Lite 正确识别。

### 8.6 社区积累

用户验证通过的适配器可以自行使用、分享或向 Lite GitHub 提交。经审核后可以进入社区适配器目录，但不得因为自动测试通过就自动合并。

### 8.7 密钥边界

- API Key 与适配器文件分离；
- API Key 不写进 Git、日志、诊断包或分享文件；
- API Key 保存在操作系统安全存储中；
- 生成适配器时不需要把真实 API Key 提供给 AI；
- 只有 Lite 的受控网络层可以使用密钥；
- 删除数据连接时同时提供删除本地凭据的明确操作。

## 九、AI Provider 与 AI Tools（后续必做）

### 9.1 产品目标

用户可以连接自己的 AI API。Lite 向 AI 提供一组受控、结构化的数据工具，让 AI 在用户发起互动时读取当前图表、K 线、指标和自选，并据此回答用户问题。

### 9.2 三层结构

```text
用户与 AI 对话
       │
       ▼
AI Provider
连接用户选择的模型服务
       │
       ▼
AI Tools
限定 AI 可以读取的 Lite 数据
       │
       ▼
Data Provider / 指标状态 / 自选
```

- `AI Provider`：连接用户选择的 AI API；
- `AI Tools`：定义模型可以调用的数据能力；
- `Chat UI`：展示对话、工具调用状态和结果。

### 9.3 AI Provider 初步范围

用户配置：

- Provider 类型；
- API URL；
- API Key；
- Model；
- 可选的兼容参数。

为减少首版开发量，实际支持顺序待定；优先考虑先实现 OpenAI Compatible，再按需求增加专用适配器。

### 9.4 AI Tools 初步范围

第一阶段只提供只读工具，例如：

- `getCurrentSymbol()`：读取当前品种；
- `getVisibleBars()`：读取当前屏幕可见 K 线；
- `getRecentBars()`：读取限定数量的最近 K 线；
- `getActiveIndicators()`：读取当前启用指标及参数；
- `getIndicatorValues()`：读取指标数值；
- `getWatchlist()`：读取本地自选。

工具必须限制数据范围和返回大小，避免无边界地把全部历史数据发送给模型。

### 9.5 第一阶段禁止的 AI 能力

- 自动交易或下单；
- 执行系统命令；
- 任意访问文件系统；
- 读取未授权的 API Key；
- 修改账户或支付；
- 静默修改自选、设置或图表；
- 不经用户发起就持续上传行情数据。

### 9.6 数据与隐私说明

AI API Key 保存在本机。用户发起 AI 对话后，为回答问题所需的选定行情和指标数据会发送给用户选择的 AI Provider。

产品不得笼统宣传“所有数据永不离开本机”。必须明确说明发送了什么、发送给哪家 Provider，并避免在日志中记录密钥和完整敏感请求。

### 9.7 AI 辅助生成数据适配器

未来 Lite 可以在“添加数据源”流程中调用用户已经连接的 AI：

```text
用户提供 API 文档
  ↓
AI 生成声明式适配器
  ↓
Lite 本地验证
  ↓
用户确认后启用
```

AI 负责理解文档和生成适配描述；Lite 负责安全、密钥、网络请求和正确性验证。

## 十、图表能力

当前选用 `lightweight-charts@5.2.1`。已经下载官方发布包，并单独建立《Lightweight Charts 5.2.1 能力盘点》。

### 10.1 可直接使用

- Candlestick、Bar、Line、Area；
- Histogram 成交量；
- 缩放、拖动、Crosshair；
- 价格轴和时间轴；
- 多 Pane 和 Pane 高度调整；
- 实时更新最后一根 K 线；
- 可见范围监听和历史加载触发；
- Marker、价格线、水印和截图；
- Primitive 和自定义 Series 扩展接口。

### 10.2 Lite 或 TradeFlow 负责

- Rust TDX 和其他数据源的统一接入；
- 品种搜索和自选；
- 周期、交易时段和聚合；
- 指标计算；
- Tooltip 和行情信息栏；
- 本地设置；
- 断线恢复和数据正确性；
- 未来的数据适配和 AI 交互。

### 10.3 第一版原则

优先使用 Lightweight Charts 的原生公开 API，不修改图表库源码，不依赖内部 DOM 或私有对象。Lite 首版不为了展示技术能力而开发自定义 Series、完整画线平台或大型插件系统。

### 10.4 v0.1 内置指标

Lightweight Charts 不提供 MA、MACD 等指标公式，只提供 Line、Histogram、多 Pane、价格线等渲染能力。Lite 需要自行计算指标。

v0.1 采用一组小而常用、足以覆盖主图线和副图线/柱的内置指标。当前范围分为必做和候选，避免首版因指标数量失控：

- `VOL`：成交量柱；
- `MA`：移动平均线，首版必做；
- 首版候选：`EMA`、`MACD`、`RSI`、`BOLL`，从中选择少量随第一版一起交付；这些指标的图库展示能力均已确认。

指标只读取当前 Lite 标准 Bar，在本地计算。参数默认值和交互细节在界面设计时固定；不使用 Pine，不允许普通用户导入源码。

## 十一、独立于 App 版本的指标生态（后期形态）

### 11.1 产品目标与边界

Lite 的应用版本与指标内容版本分离。TradeFlow 官方或社区后来增加五个新指标时，目标是不重新发布整个 macOS/Windows 客户端；普通用户在 Lite 的“指标中心”看到后，点击“使用”即可加入当前图表。

这里的“社区指标”不是 Pine、不是用户自行导入源码，也不是第三方程序插件。开发者在 GitHub Fork 后实现指标并提交 PR；只有经过 TradeFlow 审查、测试和正式发布的版本，才会作为 Lite 可选的“内置指标”出现在普通用户面前。

这不是第三条产品发布线。官网和 GitHub 仍是 Lite 产品的两条发布线；指标中心是 App 内部独立更新的内容生态。

### 11.2 用户路径

```text
Lite 读取公开指标目录
         ↓
展示新增和更新的官方内置指标
         ↓
用户点击“使用”
         ↓
下载官方签名的指标定义包 → 校验来源与兼容性 → 保存到本地
         ↓
本地读取行情并计算 → 输出标准图表元素
```

已安装指标离线时仍可使用。指标目录或下载服务不可用时，只影响发现和安装新指标，不影响现有指标和基础看盘。

### 11.3 指标包与兼容合同

暂定使用独立指标包，例如 `.tfindicator`。包内至少描述：

- 全局唯一 ID、名称、作者、版本和许可证；
- 指标运行器 API 版本与最低 Lite 版本；
- 参数、默认值、输入数据和最大回看范围；
- 受限制的计算描述或由官方运行器支持的公式定义；
- 输出线、柱、颜色、水平线、Marker 和主图/副图位置；
- 内容哈希、来源和签名信息；
- 中文或其他语言的说明、风险提示和变更记录。

新增指标只要使用现有运行器和图表输出能力，就不需要升级 App。只有指标依赖新的运行器语法、新的图表能力或安全修复时，才可以声明最低 Lite 版本，并提示用户先更新客户端。

指标定义格式的最终选择尚未决定。方向是一个不含 Pine、不能执行任意源码、只支持官方允许函数与输出类型的受限格式。无论底层格式如何，对外的指标 ID、参数、版本和输出合同保持稳定。

### 11.4 计算与渲染边界

指标定义不直接操作 Lightweight Charts。指标运行器只读取 Lite 提供的标准 Bar 和允许的内置函数，并输出标准化结果；Lite 再把结果映射为 Lightweight Charts 的 Line、Histogram、Marker、价格线或独立 Pane。

首阶段不允许指标包携带任意 JavaScript、Python 或原生代码，也不允许自行联网、读写任意文件、读取 API Key 或执行系统命令。这样普通用户点击“使用”时，不会等同于在电脑上运行陌生人的程序。

如果以后确实需要自定义绘制或更复杂的运行能力，应作为更高权限、单独评估的扩展层，不混入普通指标包。

### 11.5 指标目录与社区贡献

指标目录本身可以是公开的静态 `catalog.json`，指标包放在官网静态 CDN，并在 GitHub 保留源码、版本和可追溯记录，不需要动态业务后台。

普通用户只有一个来源：**TradeFlow 官方发布的内置指标目录**。不存在自定义指标源或本地源码导入入口。

开发者可以 Fork Lite 源码、增加指标并提交 PR。自动检查负责公式正确性、格式、测试、性能上限、许可证和危险能力；人工审核通过并由 TradeFlow 正式签名发布后，才进入官方目录。开发者自己的 Fork 可以按开源许可证自由修改和分发，但不会自动进入 TradeFlow 官方产品。

### 11.6 更新、回退与透明度

- 指标目录更新与 App 更新使用不同清单和版本号；
- 用户可以看到指标名称、作者、许可证、版本、更新时间和变更内容；开发者可在 GitHub 查看对应源码；
- 已安装指标的新版本默认提示，不静默改变现有图表计算结果；
- 用户可以保留当前版本、升级或回退到上一可用版本；
- 指标包被撤回时不远程删除用户本地文件，只提示原因并停止继续分发有问题的版本；
- 官方签名私钥不进入开源仓库，客户端只内置验证公钥；
- 社区指标不得复制无权再分发的闭源或受版权限制脚本。

具体目录托管、签名层级、审核规则、指标语言和首个支持版本继续讨论；当前先确认“无需升级 App 即可发现和使用新增指标”是后期产品能力。

## 十二、首版产品范围

v0.1 首版范围已经收敛为：

- 是可以正式安装使用的 macOS 和 Windows 客户端；

- 目标是尽量复用 TradeFlow 已有能力并迅速成型；

当前明确不进入首版的只有：

- 正式 Web 实时行情服务；

- 用户导入任何指标源码或自定义指标来源；
- 无安全边界的任意代码数据插件；
- 独立更新的官方指标目录、数据适配和 AI 接入。
